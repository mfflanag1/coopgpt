Decision: the stated protocol is a sound qualification test for these releases. The reviewed schemas do not identify a full-contract observed snapshot. This conclusion is specific to the inspected releases and contract. It does not show that public traces generally cannot support scheduling research.

Distinguish the gates
The previous solver SPEC consumes declared resource availability, owner permissions and administrative scores; it does not authenticate them. The new protocol adds empirical provenance, completeness and timing requirements to call the input an observed real snapshot. Failing that stricter gate is not a mathematical failure of the solver. The demand for a real operator comparator is conditional on claiming improvement over practice, not necessary merely to test plan feasibility. Preserve that conditional wording in the report.

Alibaba GPU2023
1. gpu_spec='nan' is explicitly documented as no GPU-type constraints. It is not an unknown/missing-value policy. The default release therefore supports a declared unrestricted type policy wherever that value occurs. A faithful reduced simulation may encode all relevant released families as allowed there. Do not claim that every blank/nan type entry makes mapping unidentified.
2. Separately, gpuspec files augment task type requirements. A comparison with the default may measure the amount and form of augmentation; it cannot establish that augmented per-job restrictions were measured. The reported production incidence motivates a scenario, not exact provenance for each assigned restriction. Any conclusion about empirical compatibility must distinguish released default policy from added scenario policy.
3. Genuine support: node CPU/RAM capacity and GPU count/type; ex-ante task CPU/RAM, whole/fractional GPU requests; QoS and event timestamps. These support request distributions, heterogeneity, queue-delay summaries after timestamp validation, and a clearly labelled static empty-cluster or simulated-state packing study.
4. Remaining full-contract blockers: no task-to-node/device allocations, no physical per-device VRAM, no job minimum per-device VRAM, no hardware owner/placement-permission mapping or numeric admission score. Total node CPU/RAM is not allocatable residual capacity. G1/G2/G3 are intentionally undisclosed types. Count-only devices may be given synthetic enumeration IDs for a simulation, but those are not observed physical IDs. CPU-milli units need an explicit consistent conversion, not rounding. A pod is an instance-level scheduling unit; grouping multiple pods into same-node gangs requires separately justified semantics.

Alibaba SpotGPU2026
1. cpu_request and gpu_request are described as requests 'by the job'; worker_num separately counts requested instances. The documentation does not unambiguously say whether resource requests are per instance or totals over all instances. Do not multiply by worker_num, omit it, or identify it with gpu_count without resolving the unit of observation. Report both fields descriptively and leave total demand unidentified where semantics matter.
2. gpu_model is documented as the job's requested card type, so it is genuine released type demand, unlike an observed-assignment field. Type names can contain nominal memory, but this is not an explicit measured per-device inventory/VRAM requirement for every code.
3. submit_time plus duration cannot establish actual start/end intervals or current availability without knowing whether duration includes waiting, retries or interruptions. No node assignment, job start timestamp or interruption/reservation ledger is supplied in this schema. Never set finish=submit+duration and call that observed execution.
4. No node/job RAM fields, explicit VRAM request, or device-level IDs. organization is a cost/administrative unit, not a hardware-owner registry or permission relation. HP/Spot is a workload class, not the solver's numeric priority. Worker groups may be distributed; same-node gang eligibility remains unestablished.
5. Genuine support: heterogeneity and submitted-demand categories, administrative concentration, HP/Spot composition, reported durations, and a useful future study of sharing between cost units once the resource-unit and execution semantics are clarified. The README's paper URL is a placeholder; this review has not authenticated the paper from that link.

Alibaba ASI GPU2026
1. Do not say this release has no GPU memory request: gpu_mem_request exists. However the inspected schema says only source-reported accelerator-memory request, without units or per-device versus aggregate semantics. avg_gpu_mem_gib is explicitly observed hourly average use, a different quantity; it cannot fill that gap.
2. The schema has CPU requests, fractional/full GPU-equivalent requests, server inventory, server IDs and hourly topology. It lacks host RAM capacities/requests, physical per-device identities and VRAM inventory, allowed owner policy and numeric priorities. gpu_spec_public is a public model bucket, not an explicit admissible-family set.
3. An hourly pod observation, GPU-hours and hourly average utilization do not identify simultaneous reservations at a decision instant. Summing every pod observed in an hour can conflate sequential occupants. Pending is a public state bucket, but rows are defined as pods observed on GPU servers, so a complete global pending queue is not established. Schedule-delay fields and execution spans do not recover precise admission events by themselves.
4. The release explicitly omits organization fields. workload_id sometimes derives from owner/workload metadata, but is not an owner authorization relation. IDs are stable only within this release; no cross-release joins are licensed by identity similarity.
5. Genuine support: hourly workload/request/utilization/priority composition, allocation aggregates and topology/fragmentation characterization at the released resolution. Large downloads do not cure schema nonidentification. The documented pod archive alone is 351,803,513,445 bytes; rejecting that download for this exact gate is justified before row analysis.

Recommended report wording
'The inspected published schemas do not supply all fields needed to reconstruct the verified model's actual decision-time input. We can audit real capacities and released requests, and can design simulations with declared assumptions. We cannot treat those simulations as observed execution fit or validated owner-authorized placement.'

No blocking flaw found in PROTOCOL. Apply the gpu_spec semantic correction above; retain actual requested-type fields and ASI gpu_mem_request rather than flattening them to generic missing data. Publish the empirical/source uncertainty separately from explicitly chosen policy assumptions. A narrow protocol failure is still useful progress when it identifies exactly which operator export or clarified source semantics would unblock the experiment.
