WHAT IS NOW RUNNABLE
collect.py runs against an existing dedicated local vLLM completions endpoint.
It records scheduled arrivals, dispatch, received output chunks, terminal status,
server token usage, warmup/drain observations and full-window selected-GPU energy.
telemetry.py records NVML board identity, power/counters and observed compute PIDs.
validate.py checks manifests, trace identity, every offered request, timeline
ordering, energy coverage, telemetry quality and declared worker residency. It
separates schema quality, measured-data readiness, paired compatibility, future
forecast calibration and future pooled-deployment validation.

Synthetic protocol/telemetry fixtures are explicitly labeled and cannot establish
measured-data readiness. No code path substitutes synthetic telemetry for a missing
GPU. Missing token usage, truncated streams and failed jobs remain failures in the
offered denominator. A stream chunk is not treated as a token. Board energy is
counted once over the full measured horizon, with idle included and no concurrent
per-request double counting. Counter and reported-power estimates remain visible.

LIMITS THAT STILL MATTER
The current host is macOS without nvidia-smi; no real GPU execution occurred.
The implementation has not yet been exercised against real NVML or a live vLLM
server. Local HTTP and NVML fixtures test protocol/accounting behavior only.
Device residency is observed; process roles, checkpoint revisions and actual
container/launch identity still require operator provenance. Dedicated full-board
compute hosts are assumed. Graphics activity, CPU/facility energy, true GPU start
and per-token timestamps, peak-power metrology and multi-host dispatch are outside
this kit. Collection success is not an empirical estimate of pooling benefits.
