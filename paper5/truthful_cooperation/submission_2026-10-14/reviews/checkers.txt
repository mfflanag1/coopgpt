FAILURE BEHAVIOR AND ALWAYS-ON CHECKS

All new mathematical requirements are explicit exceptions, not assert
statements. I AST-scanned the three scripts and found zero ast.Assert nodes.
The wrapper additionally AST-scans its seven-file source/dependency inventory
before any job. Checks therefore remain active under -O.

Child success requires both returncode==0 and a PASS marker. A thrown
require/check exception cannot pass merely because stdout already contains
PASS: the nonzero return code still fails the conjunction. The existing
child programs only emit their successful terminal PASS/JSON after their
requested checks; their error paths throw or explicitly exit 1. I inspected
those terminal paths, without re-auditing all historical checker logic.

A timeout is converted to a return code 124 record with captured output and
diagnostic. Any failed job stops the remaining loop. Overall PASS additionally
requires all five records, every record passing, and all inventoried sources
unchanged. A changed readable source produces FAIL. A missing/unreadable
source or other uncaught I/O failure exits abnormally, rather than reporting
success; an output JSON is not guaranteed for every such early failure.

The PASS-marker test is a literal substring contract with the current trusted
child programs, not a general validator for arbitrary command output. This
is adequate for the five inspected entrypoints and should not be described
as an adversarial-output parser.

ACCEPTED OUTPUT-PRESERVATION REPAIR

The initial wrapper computed sources_unchanged before calling write_text on
an unrestricted --output path. Therefore --output could name a source file
or prior report, overwrite it, and leave a newly written record saying PASS
and sources_unchanged=true. This is a concrete inconsistency with its source-
preservation promise, although it did not occur in the supplied fresh-output
replay.

The coordinator accepted the recommended repair: resolve output; refuse a
preexisting path or symlink before checks; publish with exclusive open('x')
after creating its parent directory. Exclusive creation also rejects a file
introduced between the preflight check and publication. This is a correct
repair for source/old-report aliasing under the stated local replay use.
The coordinator will test existing-output and source-alias refusal and rerun
all five jobs from a fresh extraction to bind the final wrapper hash. This
report records the accepted design, not a claim that those later tests were
already performed by this reviewer.

TWO-OWNER CHECKER: ACTUAL COVERAGE AND COUNTS

The code evaluates the repaired two-owner Shapley formula with Fraction
arithmetic over five fixed technologies and 16 two-coordinate bundles on
the grid {0,1/2,1,2}. Thus 5*16^2=1,280 full profiles is correct.

At each profile it directly checks efficiency and both singleton coverage/
nonnegativity inequalities. For two owners this implies all four coalition
cases, including the empty coalition (whose value is identically zero).
The reported 5,120 coalition count is four cases per profile; it is not
5,120 separately executed require calls or nonempty-coalition comparisons.

For each coordinate the four-level grid has 10 ordered weak-increase pairs.
Hence two-coordinate own bundles have 100 ordered weak-increase pairs, and
5 technologies * 2 owners * 16 other bundles * 100 = 16,000 comparisons.
Of these, 2,560 compare identical reports and 13,440 are strict increases
in at least one coordinate. The output key own_increases means weak
componentwise comparisons; it must not be reported as 16,000 strict changes.

The old-rule negative control is the actual full-bundle defect at M=3:
b1=(0,0), b2=(1,0) gives the old P2=0 but v({2})=1/3. The new rule tests
include overlapping bundles, zero technology and a single-form technology.
The fixture sizes and fixed two-dimensional inputs make the use of zip
well-defined here; this is not advertised as a general input parser.

LOWER SYMMETRY CHECKER: ACTUAL COVERAGE AND COUNTS

The cut enumerator is independent of the imported cut-count procedure: it
enumerates all deletion bitmasks and checks source-sink reachability, then
requires reconnection upon restoring each deleted edge. For a monotone
reachability property this characterizes inclusion-minimal cuts. The
single-pass reachability scan first verifies topological vertex labels and
nondecreasing edge tails, so it is valid on these constructed DAGs.

The three series cases have 10, 15 and 16 edges, enumerating respectively
1,024, 32,768 and 65,536 deletion subsets. Local cut counts are 5, 5 and 11;
series counts are 10, 15 and 22. The 5-edge one-branch module is a path.
For the eight-edge two-branch/one-fan module, two terminal-fan cuts plus
three choices in each of two branch paths give 2+3^2=11 local cuts. The
code checks both k times the local count and that every minimal series cut
occupies exactly one module.

The symmetry part deliberately imports graph-construction and integer
max-flow helpers; it is not an independently implemented flow solver. It
checks all 65,536 coalition masks for each of three explicit owner
permutations at one fixed asymmetric positive-capacity vector. Both the
coalition mask and owner capacities are permuted, so it tests coalition
equivariance, not a mistaken invariance with capacities left on old labels.
Branch permutations relabel their incident auxiliary edges via kind lookup.
Module swapping exchanges whole module edge blocks. All permutation maps
are checked to be bijections of the original 16-owner set.

The count 196,608 is exactly 3*65,536. The 225 positive-worth coalitions also
has a simple independent count: both common fan edges are required in each
module, and at least one of its two three-edge branches must be complete;
there are 2^6-7^2=15 possibilities per module, hence 15^2=225 in series.
These are finite witnesses at the stated profiles, not all-capacity symmetry
verification or a proof of the asymptotic lower theorem.
